# 冻结选择器组件剖析协议

本轮只做有界组件诊断，不修改控制器，不训练，不进行端到端 TTF 确认。

## 固定范围

- 复用 `sa-single-check-runtime-v1/registration.json` 已登记的 8 个案例和原历史轨迹。
- 每案例取第 0、floor((n-1)/2)、n-1 次修复前状态，去重后总计 24 个。
- 首次访问测一次，其后同一状态再测两次，共 72 次组件观测；首次与重复结果必须分开。初始状态的构造成本单独标记。
- 参考选择器与剖析选择器调用顺序按案例序号加状态位置交替，避免所有剖析都发生在 proposal 缓存已热之后。报告保留实际顺序；重复访问不代表常规在线速度。
- prefix 使用冻结显式动作、规划顺序、退火温度和接受随机数重放。总计 792 次历史修复，无自由 rollout、无新标签。
- 因包含组件计时，固定单 worker，不与其他本轮求解作业并行。每案例进程 fuse 600 秒，重放单次 PP 安全上限 300 秒、环境 3000 秒；不是扩大在线规划预算。

## 实现边界

使用 `SingleFullCheckPool.select` 的相同 Python code object，通过私有函数 globals 绑定计时包装器，不改全局函数，不重写选择代码。参考侧只捕获传给 scorer 的特征，不增加组件计时。

记录输入及最终完整 fingerprint、topology 初始化/准备、feature engine 初始化/准备、proposal、Dual16 增补、feature rows、score、最终 get_state 和包装器残差。已有嵌套计时元数据单独保存，不与其父计时相加。

状态 deepcopy、特征/候选哈希、结果比较和保存位于组件计时之外。计时包装本身仍有开销，因此这是热点剖析，不是工程加速证明。

## 硬校验

- 在每次选定状态，两侧特征逐值相同，候选/元数据/分数/选择与历史完全一致。
- 重复 proposal 后完整环境 fingerprint 不变。
- 每次实际 prefix 修复后，路径、冲突、cost 与低层累计计数 fingerprint 与原轨迹一致；PP 顺序、邻域、接受与失败原因相同。
- native、模型和历史输入 SHA 必须通过原登记验证。
- 任意错误停止，保留原始结果，不自动调参重试。
- 独立输出、原子逐案例保存、运行锁、暂停后续案例、resume；有开始标记却没有结果时必须先人工审计中断。

## 后续门控

只定位热点。本轮即使某项占比高，也不自动改模型、邻域、缓存语义、排序器或 native；必须先提出具体等价改法。不能从 24 个状态的均值推算完整 TTF 改善。

原始数据留在 `build/sa-selector-component-profile-v1`。代码、测试和本协议先本地提交登记；仅本地备份，不推送未获授权的待提交历史。
