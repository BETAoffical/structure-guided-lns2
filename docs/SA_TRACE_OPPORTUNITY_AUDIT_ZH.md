# SA已有轨迹审计：哪些改进仍值得做

## 范围

只读复核冻结独立仓库确认的128条轨迹和已登记审计证明。不启动solver、不计时、不拟合模型、不改变温度、默认控制器或native。
本轮所有窗口和分类为事后解释性分析，不是预注册确认、不生成训练标签。原SA成功率和TTF结论保持不变。

## 1. 排除重复工程优化

四种方法的全部步骤均为 `requested_collect_pp_diagnostics=false`，详细诊断数组为空。
`InitLNS::runPP` 已直接进入 `runPPWithoutDiagnostics`。因此再次关闭逐agent诊断不会带来收益；
CPLNS作者参考的无分配观测改造也不是当前运行时尚未使用的同一项优化。

原Dual16+SA的32条轨迹累计：

| 层级/部分 | 秒 | 解释 |
|---|---:|---|
| 整体循环 | 549.3338 | 含预算失败的实际循环时间，不等于只成功任务均值 |
| reset | 37.5835 | 初始化等 |
| 选择阶段 | 120.9009 | 上轮单次检查已证明可降低此部分，不能再次计为新机会 |
| PP修复 | 362.3299 | 占整体65.96%；不是全部都属于SIPPS搜索本身 |
| native维护 | 0.3614 | native子阶段 |
| native状态快照 | 0.8271 | native子阶段 |
| state转Python | 3.6426 | binding子阶段 |

表中子阶段有嵌套关系，不把各行相加为总时间。现有计时未进一步拆开PP里的 `findPath`、冲突对更新、路径表插入/删除及回滚。
不能假定362秒都是可删除的维护开销，也不能未经测量就宣称主要耗时来自某个具体底层函数。
当前状态转换和维护的已知开销远小于PP；没有找到第二个可直接照搬上轮的25%级选择器删减点。

## 2. 接受上升：不是所有控制器处于同一探索强度

| 指标 | Official+SA | Dual16+SA |
|---|---:|---:|
| 32条成功数 | 30 | 31 |
| 完成PP后较差尝试 | 2749 | 719 |
| 接受上升 | 2147 | 710 |
| 较差尝试的平均接受概率（按事件） | 77.63% | 99.16% |
| 平均接受概率（先按episode均值，再平均有此事件的episode） | 91.04% | 99.44% |
| 迭代次数中位数 | 182.5 | 79 |
| 最大迭代次数 | 897 | 330 |

两者都用 `T=1000*0.99^decision`，但相同墙钟预算内执行的轮数不同，冷却进度也不同。
接受率差异还受冲突增量、访问状态与长轨迹的事件权重影响，不能把差异全部归因于冷却。
这一点说明：相同的公式不是相同的实际探索强度，也不意味着已证明应该调整温度。

Dual16+SA的719次较差尝试中只拒绝9次，分布在5条轨迹。当前组合接近宽松接受，但不能直接等同无条件接受：少数拒绝也可能改变整个后续轨迹。

## 3. 接受后多久出现下降

定义：在一次上升动作**之后**继续观察，何时首次降到该动作执行前的冲突数以下。回到相等不算严格下降。
后续不足整个窗口且尚未成功时标记右删失（未知），不当成窗口失败。提前可行属于已知下降。

Dual16+SA共710次接受上升：

| 后续窗口 | 降到接受前以下 | 完整窗口仍未降到以下 | 观察不足 |
|---|---:|---:|---:|
| 4步 | 440 | 270 | 0 |
| 16步 | 566 | 143 | 1 |
| 64步 | 643 | 66 | 1 |

观察到的完整剩余轨迹中，709次最终降到接受前以下。但是31/32条轨迹成功，本来就会最终降到0；
因此709/710不等于“709次上升都对求解有益”，更不是拒绝分支的反事实比较。
窗口可重叠，同一段恢复可能被多个上升事件共同计入；事件不是独立任务，不把它们当成710个独立样本。

实际意义：大量上升事件在4步窗口尚未出现严格净下降，之后才出现下降。
这不能给出在线决策规则，但足以警惕把“4步没收益”直接当作必须回退的条件。
是否拒绝会更快，必须从同一状态保留拒绝对照才能回答。

## 4. 成功与失败的边界

- 相对Dual16新增成功的10个案例全部出现过接受上升；这是关联，不证明每个上升动作不可或缺。
- Dual16+SA仍有6个成功episode没有接受过上升。
- 唯一失败为m00高密度/seed103：初始265对，330步后剩4对，接受过77次上升。
- 所以该失败不能解释为“从未允许探索”；也不能仅根据较多上升次数判定它们造成失败。
- 保留旧结论：完整贪心未显示可以直接替代SA；均匀探索与模型有覆盖/效率取舍；固定一比一双轨已有节点代价负面结果。

## 5. 下一步：只验证一个尚未解决的问题

**优先检查这9次拒绝是否有实际保护作用，而不是扫描温度或重训。**

建议单独登记有界、非计时的配对分支探针：

1. 使用9个已发生拒绝的事件，固定原状态、候选、agent集合、PP顺序和尝试路径；包含全部5条来源轨迹，不按后续结果挑选。
2. 先严格复现原分支；然后只改变这一事件的接受/拒绝决定，后续回到同一冻结模型和SA调度。
3. 固定有限后续步数、节点/时间安全上限；完整比较新路径/冲突、累计搜索量及可行性；未到终点明确为有限窗口证据。
4. 少数拒绝明显保护搜索：保留SA，才考虑是否存在可观察的风险特征。
5. 拒绝没有稳定价值：再讨论独立“完整PP+无条件接受”简化对照，不能直接根据事件很少就删除冷却。
6. 结果混合或未知：保留当前已有效版本，不追加温度网格、停滞救援链或RL。

这只是建议，**本轮没有执行9事件分支探针，也没有新增求解任务**。
该探针不是又一次确认“上升后可能下降”，而是针对实际分歧点验证“拒绝有没有帮助”。
仍不能由5条旧轨迹推导通用在线阈值，不能改变原独立确认结论。
旧记录没有保存被拒绝的完整候选路径，不能离线翻转接受标记来生成反事实结果。
必须重新执行同一完整prefix，验证原分支的状态、PP顺序、计数与接受决定，再在分支运行中保存尝试路径见证；无法复现时停止，不生成比较标签。

工程侧若单独继续，先对PP内部做隔离、动作等价的成本定位；没有分项证据前不改搜索、排序比较器或路径表语义。

## 验证与保留

- 128/128冻结轨迹SHA与101个独立审计证明SHA通过；逐步复核冲突连续性、接受概率与决定、TTF锚点和计时字段。
- 新统计器最初把未执行PP误当成失败回滚，导致校验停止；修正为独立 `pp_not_run` 分类，未修改原始数据。
- Official有1567次、Official+SA有841次PP未执行；这类记录不能当作已经尝试修复后的失败。
- Windows Python缺少pytest，未安装依赖；改用现有WSL pytest，最终15项通过。
- 新脚本不调用求解器。本轮未重新运行CTest或正式计时，也不把旧CTest结果当成本轮执行结果。
- 源码/数据恢复点：`pre-sa-trace-opportunity-audit-20260912`；输出 `build/sa-trace-opportunity-audit-v1/report.json`。
- 输出明确标注posthoc、窗口重叠、无因果/在线门控结论。没有训练标签、没有自动策略晋级。
