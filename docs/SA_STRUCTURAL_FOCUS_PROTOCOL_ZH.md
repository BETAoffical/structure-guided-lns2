# 结构化邻域次核心检查：先冻结输入与边界

## 问题和历史排重

上一轮47根中35根由Dual16选择结构化邻域，但没有同来源同大小成员替代。本轮只问：在这些原输入上，换一个当前冲突核心、保持16人和原补齐规则，是否真的产生不同集合？

这不是首次提出多核心。历史CausalClosure包含多个component/事件时间核心，StructPool扩过结构族及8/16/24/32，SafeSlot和SlotPool做过门控/压缩。它们分别留下覆盖、额外开销和闭环风险。本轮不重做闭包、大小网格、标签或评分器；只将当前固定Dual16的“选哪个核心”与“如何补齐成员”分开，核实下一项假设的可执行性。

## 固定算法

- 使用同47根、8张已查看开发地图；不按任何修复结果筛选根。非结构化anchor的根保留，但不生成干预候选。
- 每个冲突component按原规则排序：内部冲突事件数、成员数降序，component ID升序。排除没有冲突事件的孤立agent。
- hotspot沿用`(time // 4, cell)`，按事件数降序、时间与cell升序。相同seed-agent集合的多个桶只保留第一个，防止同一对车在多个格/时间出现被误认成不同核心。
- 对原anchor所属的component/hotspot族，只用第二个不同核心生成一个变体；不足两个时记缺失，不放宽、不改用第三名。
- 完整复用`_ranked_seed_neighborhood`与补齐规则，名义和实际size均为16。不添加阻挡者闭包，不修改规划顺序、PP、SA或正式候选池。
- 若两个核心经过补齐后集合相同，记录`same_after_fill`，不能再往下扫描直到找到不同集合。变体若已经在原池中，单独记录，不能当新动作。
- 原anchor同时标为component/hotspot时，两族各最多一个变体；最终唯一agent集合去重统计。变体使用独立研究身份，不能伪称原生成器已提供同来源候选。
- 47根的两种原首核心生成结果都必须逐成员复现原池候选，重建冲突边必须与源状态一致；任何不一致立即失败。

只使用当前路径、冲突事件、agent身份和冲突度。生成函数不读取模型分数、历史成功见证、修复后路径、H32结果。标签文件只读取候选ID来检查是否已有同组anchor对照，不能按标签值选择变体。

## 执行和解释

新增入口只提供`prepare / materialize / verify`。默认20个进程，允许降低worker数；0次reset、0次PP、0次模型拟合、0个新标签、无正式TTF。输出单独放在`build/sa-structural-focus-v1`，原输出不覆盖，登记输入和实现SHA，运行锁阻止重复启动。

报告适用根、第二核心缺失、补齐后重合、不同集合、原池已包含、可复用标签、逐地图分布。没有性能门槛，因为没有执行动作。

如果只有少量不同集合，不能自动换成top-k、扩大size或改触发门槛；如果不同集合很多，也只能说明可比较，不代表成员缺陷、长尾修复或模型训练价值。原来的35根没有变体符合旧生成合同，不是代码bug。

本轮结束后根据可执行范围决定是否值得单独登记有界长期对照；不自动训练、补采或计时。未来如做一次根替换加旧策略续跑，只能支持这种干预，不能直接部署成每步新策略。

## 验证

单元测试覆盖次核心选择、忽略孤立agent、热点重复桶、确定性、非连续ID、输入字段隔离、冲突边一致、原首核心复现及重复集合分类。旧模型、native、候选生成和报告SHA不改变。

```text
python scripts/probe_sa_structural_focus.py prepare
python scripts/probe_sa_structural_focus.py materialize --workers 20
python scripts/probe_sa_structural_focus.py verify --workers 20
```

实现与协议先作本地提交，再执行正式开发根的生成检查。没有新的远端推送授权，只保留本地提交和已验证增量备份。
