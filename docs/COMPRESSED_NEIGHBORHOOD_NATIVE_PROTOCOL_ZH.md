# 16/12/11车集合的有界原生PP验证

## 冻结问题

只使用`case-6542dfb0660a`历史第254步之前的状态，42对冲突。原16车随机集合在这一历史事件将冲突降至34对。比较原16车与路径消融得到的12/11车集合，检验没有已知新路径输入时，PP是否仍能产生类似进展。

这是一个已经查看结果后选定的成功状态，不是独立确认，不用于推广整体成功率、长尾或跨地图改善。失败状态、V2案例和完整闭环不在本轮追加。

## 执行顺序

1. 冻结完整253步prefix、源状态、历史动作/结果、native、代码和输入SHA。
2. 原16车使用历史原动作和原预算复现一次，要求实际PP顺序及完整修复后fingerprint与历史一致。不通过则停止，不进入随机组。
3. 固定8个新随机顺序，每组各执行16/12/11车，24个独立进程作业。最多20个同时运行，单作业外部fuse300秒，新修复PP预算10秒。
4. 每个作业独立reset并重放完整253步前缀，验证每步完整fingerprint与实际PP顺序。只执行一次新候选修复，不做后续延续。

随机种子使用固定`compressed-native-v1/20260914`命名空间。每组先产生16车顺序，再将同一顺序限制到12/11车成员，保留共同车辆的相对顺序。三者使用相同action seed和独立命名空间的PP seed，在跳过默认shuffle后固定低层随机流起点。

这是使用现有显式repair_order接口的受控机制消融，不等于原生默认shuffle；不同集合会改变低层调用数量和后续随机消耗，不能声称每次搜索完全配对。原生实现、默认策略和排序器不修改，不开启额外PP诊断分支。

## 指标与事先边界

报告每组剩余冲突、严格下降、达到不超过34对的次数、接受/回滚、失败agent与原因、低层节点；完整状态保存并重新检查路径合法性和冲突边。

压缩组只有满足以下条件才记为`bounded_mechanism_signal_only`：8次中至少6次不超过34对，平均剩余冲突不高于原16车，且无时间删失或实验错误。其他情况为未通过；存在预算删失时单独标记，不能解释为无解。

本门槛不证明压缩模型有效或比16车更优，更不授权自动闭环、扩采或RL。没有通过时不追加随机种子、不扩大预算或修改集合。

保留PP runtime仅作开销记录；并发结果不进行TTF或单worker速度比较。目标仍是确认低成本修复机制是否有现实机会，而不是将固定路径拼接当作算法收益。

## 安全与交付

历史复现与随机组分别运行。`collect`只在qualification成功后执行，支持完整结果级续用；错误或外部fuse终止采集，不自动重试。`STOP_AFTER_JOB`标记停止继续派发，已运行作业完成后暂停。

输出在`build/initlns-compressed-neighborhood-native-v1`；协议、代码、测试与计划SHA在正式随机组运行前推送。源码与报告提交Git，完整状态及运行日志留在build。默认Official、V2、Dual16保持不变。
