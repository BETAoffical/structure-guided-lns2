# 冻结 SA 选择器组件剖析结果

## 本轮结论

已完成 8 个案例、24 个冻结状态、72 次组件观测及 792 次历史修复重放。特征、候选、元数据、分数、选择、PP 顺序和完整状态均保持一致，无错误或安全超时。

本轮只定位热点，**没有修改求解器或证明新的 TTF 加速**。最值得先验证的是现有拓扑/路径热度增量接口在 SA 入口的复用，不是换模型或继续删回退。

## 代码中具体发生了什么

`SingleFullCheckPool.select` 调用 `self.topology.prepare(state)`，没有传入 `changed_agents`。

`TopologyAnalysisCache.prepare` 已提供增量热度更新：

1. 当前未提供变化集合时，每次 `_reset_heat(paths)`，遍历所有路径重算访问次数和经过该格子的 agent 数。
2. 提供有效变化集合时，已有 `_update_heat` 可以减去旧路径、加上新路径。
3. 但 native prepared analysis、冲突事件及其他准备工作仍会执行。即使增量热度完全无开销，也不能声称消除了全部拓扑准备成本。
4. 已有 prepared capsule 被特征阶段复用。特征返回的若干 `state_*_seconds` 是 capsule 携带的准备阶段计时，不能因它们再次出现在特征元数据里，就断言状态被重复分析或将这些数值二次相加。

此前 [工程审计](SA_ENGINEERING_SPEED_AUDIT_ZH.md) 已将增量拓扑/路径热度列为“之后评估”，本次提供了当前 SA 入口的具体成本依据。不是重新开发已有静态缓存或 prepared 复用。

## 下一步仅做一个独立优化

拟验证现有增量热度接口，保持完整冲突分析、模型、候选、fingerprint 和 PP 全部不变。

- 使用独立 selector，不覆盖冻结 `SingleFullCheckPool`，不改 native。
- 变化集合必须相对于缓存实际保存的上一状态计算。不能只相信“上一次请求的邻域”，尤其当中间跳过选择、连续修复或发生拒绝回滚时。
- 保留周期性完整 shadow 校验；验证接受、拒绝、路径长度变化、终点等待、非连续 ID、空变化集合以及缓存失效。
- 同一状态的新旧拓扑分析、heat、特征、候选、评分及动作必须完全一致。
- 先做固定窗口组件比较，包含变化集合识别和 shadow 校验的成本。只有实际净省时才考虑端到端验证；不按某个成功样本调整阈值。
- 若局部热度只占很小比例或识别/校验开销抵消收益，则保留负面结果，不直接转成全量增量冲突图重构。

本轮未自动实现此优化，也未开启新 native 或完整计时实验。之前的 SA 拒绝分支结论和正式成功率/TTF 结果均不变。
