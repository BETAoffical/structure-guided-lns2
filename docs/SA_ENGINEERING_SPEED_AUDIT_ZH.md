# Dual16+SA工程加速初查

## 结论

有不改变模型和动作的工程空间。本轮仅新增诊断入口和测试，**没有修改生产控制器、
官方修复器、模型、退火参数或已完成的128条正式结果**。

已验证的第一项是合并重复状态检查：24个状态中，候选、元数据、评分和最终选择完全一致，
选择阶段耗时下降的逐状态中位数为21.68%。依照历史耗时占比推算，固定轨迹下整体时间
可能下降约4.77%；这不是正式端到端TTF测量，也不保证固定时限下的最终路径/成功数不变。

## 当前时间花在哪里

从上一轮128条冻结记录读取分项时间并检查SHA。以下为Dual16+SA的32条运行累计，
包含失败运行实际执行的循环时间，不是只取成功任务：

| 部分 | 累计秒数 | 循环占比 |
|---|---:|---:|
| 原生PP修复 | 362.33 | 65.96% |
| 候选、特征与评分 | 120.90 | 22.01% |
| 初始reset/PP | 37.58 | 6.84% |
| 转换、记录及其他 | 28.52 | 5.19% |
| 合计 | 549.33 | 100% |

即使选择阶段耗时减半，固定轨迹下也只减少约11%的总时间。
不应把“选择阶段快21.7%”写成“算法TTF快21.7%”。

历史优化已经包括grouped/batched proposal、native特征、prepared分析复用、静态地图缓存、
native pairwise评分和fingerprint编码快路径；本轮没有重新把这些当作新增贡献。
上一轮事后审计累计47.76分钟不属于算法TTF，加快审计不能算求解加速。

## 找到的冗余

`scripts/run_sa_wall_clock.py::TimedPool.select` 调用
`generate_online_candidates(..., verify_full_state=True)`，其内部会：

1. 比较原生state revision，检查proposal没有改变结构状态。
2. `get_state()`、递归`_plain()`并计算完整fingerprint。

随后TimedPool完成特征与评分，又调用一次`get_state()`并重新计算完整fingerprint。
这两次快照与完整哈希都在同一次选择中。

诊断变体仅将内部`verify_full_state`设为False：仍保留原生revision前后检查，
仍保留外层末尾完整fingerprint比较。没有改变fingerprint字段、proposal seed、候选上限、
去重、排序或PP动作。原生版本不支持revision时，现有生成器仍自动执行完整检查。

实现位于 `scripts/audit_sa_engineering_speed.py::SingleFullCheckPool`，使用临时补丁做
单进程机制测试，**不是可直接部署的生产类**。正式接入时应采用显式运行时参数，
不能把临时全局补丁带入并发控制器。

## 微基准结果

- 固定4张已查看地图m00/m02/m04/m06，15%与25%两个负载、solver seed101，共8例。
- 每例最多检查最初3个修复决策状态，本次共24个状态，不代表完整长尾阶段。
- 两种选择器分别预热，每状态8轮、交替先后顺序，共384次计时选择。
- 每次传入新的状态副本，副本构造位于计时外，避免重复对象身份产生不现实的缓存收益。
- 选择输出逐项相等；状态在重复proposal后不变。
- 每个案例向末尾快照注入错误iteration，8/8均触发完整fingerprint拒绝。

| 指标 | 结果 |
|---|---:|
| 每次完整状态读取 | 2次 -> 1次 |
| 24个状态中更快的数量 | 24/24 |
| 逐状态耗时下降中位数 | 21.6800% |
| 逐状态下降范围 | 18.18%-30.33% |
| 各状态中位耗时再取算术平均 | 39.91ms -> 30.72ms |
| 候选/评分/选择不一致 | 0 |
| 最终状态防护故障注入 | 8/8拒绝 |

两种百分比聚合方式不相同；21.68%是逐状态相对下降的中位数，不是对39.91与30.72直接计算。
这些是热选择器组件计时，未测冷启动、完整闭环或最终可行时间。
构造后续诊断状态时使用5秒单步PP预算，不将其伪装成原60秒正式轨迹重放。

## 剖析与后续优先级

cProfile显示，递归容器转换、完整fingerprint、候选后处理和拓扑准备比模型评分更值得先看。
评分已走原生实现；这次24次剖析调用中评分累计约0.037秒，整个选择累计约1.406秒。
剖析器会放大Python调用开销，这些数只用于定位，不当作真实TTF比例。

1. **先接入单次完整检查的独立实验运行时。**保留默认参考实现与所有故障防护，
   增加proposal超时、revision变化、空候选、末期状态和完整固定动作前缀测试。
2. **再做小规模串行端到端配对。**模型、候选、SA和PP不变，先证动作与路径等价，
   再观察真正TTF；到预算边界时，较快执行能多做步骤，应单独报告，不强求超时轨迹等长。
3. **之后再评估拓扑/路径热度增量准备。**当前仍会全量遍历路径。必须验证失效与回滚，
   防止缓存用旧冲突图或漏掉外部agent变化。已有prepared和静态缓存不重复开发。
4. **最后才考虑PP内部工程优化。**它占约66%，但改优先队列顺序、tie-break或截断不是纯工程，
   容易重演旧native不一致问题，不能直接修改官方baseline。

不优先换GPU/重训模型，不减少候选数量，不改变退火温度或接受概率，
也不把多worker抢占资源得到的总实验吞吐量当单例TTF提升。
