# 优化后 Dual16+SA 的成本归因

## 本轮范围

只读复核上一轮单次完整校验实验的 32 条串行轨迹，包括原运行时和优化运行时各 16 条。共 4 张地图、8 个案例，每案例每运行时重复两次；全部成功。没有重新求解、计时、训练或修改控制器。

本轮补充的是**优化后的成本分解及低冲突阶段占比**，不是再次验证相同的 fingerprint 加速，也不是一项新速度提升。不能用这批全成功案例估计全体困难任务的失败长尾。

## 不重叠的总时间分解

以下每列合计是首次可行 TTF，不是 `loop_end_seconds`，不含最终解之后的 trace 编码、校验和写出。以前步骤的 trace 编码仍发生在 TTF 之内，不能事后扣除。

|部分|原运行时累计秒|优化后累计秒|优化后占比|
|---|---:|---:|---:|
|reset 与初始 PP|17.4626|17.6653|7.041%|
|邻域选择，含生成、拓扑、特征、推理及选择内校验|67.1146|50.0199|19.937%|
|native PP，含搜索和 PP 内路径管理|169.0335|167.1657|66.630%|
|native step 中 PP 以外工作|0.7077|0.7162|0.285%|
|solver 调用包装，排除 native step|0.0707|0.0705|0.028%|
|binding 导出与转换，排除 solver 调用|1.9896|2.2386|0.892%|
|Python 循环其余工作与未细分间隔|12.9175|13.0087|5.185%|
|总 TTF|269.2963|250.8847|100%|

核算逐事件验证嵌套计时关系，不把 `native_step_seconds`、`native_replan_seconds`、`binding_total_seconds` 重复相加。Python 残差包含 `_plain`、前一步 delta 编码、动作构造、循环检查及可能的调度等待等，现有数据不能将其全部归因于某个函数。

`native_neighborhood_generation_seconds` 在这里是显式动作进入修复器的工作，不是 Python selector 枚举 Target/Collision/Random 的总成本。后者属于表中的邻域选择。

## 低冲突仍然耗时

按每次修复前的唯一冲突 agent 对数分组。SA 可以重新增加冲突，所以这是状态严重度分组，不是三个连续且不可返回的时间阶段。

|修复前冲突对数|修复次数|优化后间隔累计秒|占总 TTF|其中 PP 秒|其中选择秒|
|---|---:|---:|---:|---:|---:|
|1–10|852|100.6033|40.099%|66.6014|25.4405|
|11–100|556|95.9482|38.244%|71.4756|18.6431|
|超过100|176|36.6680|14.615%|29.0887|5.9363|

剩余 7.041% 是 reset。这里的间隔包含前一条记录收尾，不能当成纯修复函数计时。

1–10 冲突状态贡献 53.79% 修复调用，说明即使本轮均能成功，最后少量冲突也会重复消耗计算。但这不是所有低冲突状态都困难，也不证明改小邻域或强制回退会更好。

## 排除哪些重复或低收益改动

1. **不再做关闭 PP 详细诊断。** 保存的所有步骤都已关闭。
2. **不再重复 batch proposal、native 特征和静态缓存。** 这些已在运行时使用；prepared 拓扑复用与单次完整 fingerprint 检查也已实现。
3. **不优先改修复内部快照和绑定层。** 当前 native PP 之外、solver 包装和 binding 导出合计约 1.206%。这是这些已测部分完全消失且其他成本不变时的理想极限，不包含选择器内部的最终完整校验。
4. **不把慢归咎于拒绝/回滚。** 优化运行时所有 `acceptance_rejected` 尝试的整个 PP 合计 1.8900 秒，约占总 TTF 0.753%。这包括已完成搜索，并不是回滚计时。具体回滚仍未拆分，删除拒绝还会改变轨迹，不能按此估算实际收益。
5. **不因低冲突调用多而恢复旧停滞阈值链。** 上一轮 9 个拒绝点已发现保护、受益及下一步汇合三种情况，没有通用接受规则证据。

历史依据见 [工程审计](SA_ENGINEERING_SPEED_AUDIT_ZH.md)、[已完成的运行时加速](SA_SINGLE_CHECK_RUNTIME_RESULTS_ZH.md)、[拒绝分支诊断](SA_REJECTION_BRANCH_RESULTS_ZH.md) 和 [选择器因子实验](SA_SELECTOR_FACTORIAL_RESULTS_ZH.md)。

## 有哪些真正可研究的空间

**优先级一：细分现有选择阶段，寻找低风险的冗余遍历。** 约 19.94% 的时间仍在选择阶段。如果能够把这一整段减半且所有动作及其他成本不变，总 TTF 理想下降约 9.97%；不是已测加速，也不能据此承诺实际收益。

当前 `SingleFullCheckPool.select` 接收了生成器、特征和 scorer 的计时返回值，但没有将其存入这批轨迹。下一步可用独立剖析入口保留它们，同时细分 topology prepare、完整 fingerprint 和候选增补。不能把这些计时补写进历史 trace。

**优先级二：细分 PP，而不是直接改 SIPPS。** `runPPWithoutDiagnostics` 同时包含 `findPath`、`updateCollidingPairs`、路径表插入、接受判断、删除与恢复。现有 66.63% PP 总时间不足以证明内存分配、冲突扫描或回滚哪个占主导。SIPP 中确实存在节点分配与释放，但仅看到 `new/delete` 不是采用内存池的依据；内存布局及 tie-break 风险也须先排除。

**次优先级：Python 状态转换与 trace 编码。** 循环还有约 5.19% 未细分成本，可能包括递归 `_plain` 和 delta 编码。先测量再决定；直接去掉复制可能影响对象别名、缓存失效与旧轨迹保存，不能只凭 JSON 数据看起来相同就删除。

## 下一步的最小验证范围

- 只做独立组件剖析，不改默认运行时与 frozen native，不训练、不增加候选、不启动正式 TTF。
- 从这 8 个案例的现有状态按案例及早/中/晚决策位置固定取样，最多 24 个状态，不按耗时或收益挑选。
- 先完整重放并验证候选、分数、动作、路径及低层计数；等价性不通过立即停下，不比较时间。
- 对同一状态的选择阶段记录分项并与原 selector 对照；剖析只运行短窗口，严格区分组件时间与端到端 TTF。组件计时单 worker，准备和只读校验可并行。
- 只有确认某项是明显热点且存在具体等价实现，才实现一个独立优化并验证。在看见热点前不动邻域数量、接受温度、PP 顺序或搜索排序。
- PP 的更细剖析若需要新 native，另建诊断构建目录并登记 SHA，先确保动作、路径和节点计数一致；不能覆盖当前正式 `.so`。不因为“PP 占比大”直接开启大规模底层改造。
